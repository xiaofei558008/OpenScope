# Adversarial Review — OpenScope Architecture Spine

**Date:** 2026-08-08
**Lens:** 构造两个一层之下的单元，各自字面遵守全部 AD 却仍可能互不兼容。
**Verdict:** FAIL（发现 4 个可关闭的洞，建议新增 AD-10/AD-11）

## 发现

### 1. 叶子 id 在 ELF 重载后无稳定性保证（模块间/模块与框架冲突）

两个窗口模块都遵守 AD-3/AD-5：加载时用 `os_fw_leaf_find` 拿到叶子 id 并缓存。ELF 重载后框架重新扁平化叶子表——目前没有任何 AD 承诺叶子 id 在两次加载之间保持稳定（排序/数量都可能变）。模块 A 缓存的 id=7 在重载后可能指向完全不同的变量；两个模块因此可能观测到同一 id 的不同语义。

**建议：** 新增 AD：叶子 id 仅在单次 ELF 加载生命周期内有效；模块必须实现 `on_reload` 并按名称重新解析，框架不承诺 id 跨重载稳定。

### 2. 环形缓冲/样本分发的所有权未定义（多消费者竞态）

AD-4 只规定"样本必经环形缓冲"。若驱动模块自己向环形缓冲写样本、或两个窗口模块各自消费并修改样本缓冲，会出现双写者/双消费者竞态，且 `ring_cs` 只保护框架内部的队列。

**建议：** 新增 AD：环形缓冲与样本对象为框架独占所有权；模块只能经 `on_samples` 只读消费副本/指针，禁止直接访问 `g_app.ring`。

### 3. 原始字节序与时钟源未约定（多驱动分歧）

AD-4 规定 `ts_us` 但未约定时钟源与 `raw` 字节序。一个按 ARM 小端返回 raw 的驱动与一个按大端返回的驱动，会让同一叶子解出不同数值（`os_decode_value` 按小端解释）。

**建议：** 新增 AD：`OS_Sample.raw` 一律为目标机字节序（框架按叶子类型解码），`ts_us` 统一用 `os_time_us()`（Windows FILETIME→Unix 微秒）；驱动不得自行解码/转换字节序。

### 4. 写值与轮询读的并发、ELF 重载与采集线程的并发均未约束

写值（`os_fw_write_leaf` → OS_CMD_WRITE_MEM）与轮询线程读同一地址可能交错；ELF 重载刷新叶子表时采集线程仍在遍历叶子，产生悬空/错位访问。

**建议：** 新增 AD：驱动模块内部用互斥序列化 READ/WRITE；ELF 重载必须在采集暂停（或 generation 计数）下进行，重载完成后才恢复轮询。

## 结论

将上述 4 项合并为 AD-10（叶子 id 生命周期 + 重载与采集互斥）与 AD-11（样本所有权只读 + 字节序/时钟约定 + 读写序列化）后，可关闭全部发现。
