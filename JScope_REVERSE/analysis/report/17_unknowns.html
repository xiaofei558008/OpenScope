17真机实测：三项未解项的实验结果

上一轮把 10 项未解收敛到 3 项（都需硬件）。本轮用 J-Link PRO（SN 174504925）+ STM32F303RC（JTAG 4 MHz） 实机验证，三项全部闭环：HSS 能力与 flags 语义（自建 ctypes 台架直接调 JLINK_HSS_*）、 采样率 10 倍因子（真值对照）、RTT-Plus 配置串逐字节（主机侧伪目标端）。

17.1 ① HSS 能力位与 flags 语义（实验：直接调用 DLL）

台架：tools/jlink_lab.py（Python ctypes → JLink_x64.dll，绕过 J-Scope 直接调 API）

JLINKARM_EMU_HasCapEx(0x35) = 1                     // J-Link PRO 支持 HSS
JLINK_HSS_GetCaps → 64 00 00 00 | a0 86 01 00 | 02 00 00 00 | 00 × 20
   +0x00 maxBlocks = 100              // 变量数上限（超出 → rc=-3）
   +0x04 maxRateHz = 100000           // → 最小周期 10 µs（正是 J-Scope "老 DLL → 10" 的来源）
   +0x08 capBits   = 0x2              // bit1 置位 → flags.bit0 会被保留
   其余 20 字节为 0（DLL 写满 32 B）
flags末时间戳 ÷ 墙钟时间戳单位中位采样间隔（请求 1000 µs 时）
00.001毫秒2 ms
10.994微秒2 ms
20.001毫秒4 ms
30.993微秒3 ms

结论（实测）：flags.bit0 = 时间戳时基选择 —— 1 = µs，0 = ms （两种周期各测两次，比率 0.99 vs 0.001，恰好 1000×，无歧义）。 bit1 会改变实际采样间隔（同周期下 2 ms → 3–4 ms），机制在探针固件侧，未继续深挖。

这解释了 J-Scope 为何恒传 flags=1：它要 µs 时间戳； 而 DLL 只在探针 caps+8.bit1 置位时才保留该位（J-Link PRO 上置位 ✓，所以 J-Scope 的 µs 语义成立）。

17.2 ② 采样率 10 倍因子（实验：真值对照）

量测法结果
真实采样率 台架以 period=100 µs / flags=1 / 1 个 uint32 变量 直接跑 HSS，统计 3 s 内读到 29,679 个样本 9,868.8 Sa/s
（时间戳中位增量 99 µs，末值÷墙钟 0.995）
J-Scope 显示值 同一配置下用用户工程 f303_debug.jscope 采样 15 s，读状态栏 81 kSamples/s
（Buffer: 64 MB, 2%）
比值 显示值 ÷ 真值 ≈ 8.2×（公式推导为 10×）

结论（实测）：J-Scope 状态栏的 Samples/s 被放大约 8–10 倍 —— 请求 10 kHz、真实约 9.9 kHz，却显示 81 kSamples/s。 与静态结论（numSamples × 10⁷ / elapsed_µs，单位链经两处独立调用点确认）一致： 这是 J-Scope 的一个真实缺陷，OpenScope 若显示采样率务必自己按 样本数/时间 计算。

附带实测：J-Link PRO 在 100 µs 周期下能跑到请求速率的 ~99%（9.87 kSa/s）—— 远好于之前台架在 1000 µs 周期下看到的 ~300 Sa/s（那是 Python 轮询过慢所致，非探针限制）。

17.3 ③ RTT-Plus 配置串逐字节（实验：主机侧伪目标端）

方法：MCU 固件未插桩 RTT，因此由主机在目标 RAM 里伪造 SEGGER RTT 控制块 （0x20004000：ID "SEGGER RTT" + 上行 JScope_Data + 下行 JScope_Config， 缓冲各 4 KB/1 KB），再让 J-Scope 以 RTT-Plus 工程（两个符号：index@0x20000000、g_b@0x20000004，各 4 B）采样。 J-Scope 找到通道后把配置写进下行缓冲 —— 直接读目标内存即得到原始字节。

JScope_Config 下行通道实收 48 字节（WrOff 从 0 推进到 48）

+0x00addr0x20000000
+0x04= 0保留
+0x08size4
+0x0C= 0保留
addr 0 size 0 → 每变量 16 B；第 3 个 16 B 槽全 0 = 终止项 
// 实测原始字节（48 B = 16×3）
00 00 00 20 00 00 00 00 04 00 00 00 00 00 00 00    // addr=0x20000000  ?=0  size=4  ?=0
04 00 00 20 00 00 00 00 04 00 00 00 00 00 00 00    // addr=0x20000004  ?=0  size=4  ?=0
00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00            // 终止（整个 16 B 槽为 0）
对照结果
与本文 §7 的静态分析 完全一致：每条 16 B、+0 Addr / +4 0 / +8 Size / +12 0、按变量选择顺序排列 ✓
与 SEGGER UM08028 文档 不一致：文档写「<4B Size><4B Addr> 成对 + 8 字节 0」。 按文档实现的目标端会把 0x20000000 当成 size 读 —— 必须按实测格式实现
终止项 实测为整整 16 B 的零槽（静态分析曾推测 12 B，实测更正是 16 B）

应答握手也一并实测到了：伪目标端没有回应时，J-Scope 弹出 "Timeout. No response from target! Retry?" —— 印证 §7 分析的"配置下发后等待目标端回复"， 目标端必须在收到配置后往上行通道写回 256 字节 0（或写错误串让 J-Scope 显示），否则 J-Scope 判定超时。
