05HSS 高速采样协议（异步）

JLINK_HSS_* 是 J-Link SDK 的能力，SEGGER 未在公开手册里给出调用契约。 本节给出的是从 JScope.exe 反汇编还原、并用 JLink_x64.dll 内部字符串交叉验证的完整契约。

5.1 变量描述符数组 观测

FUN_140041f30 构造并下发（括号内为 JLink_x64.dll 中的对应日志串，证实了签名）：

// JLink_x64.dll: "HSS started: %d DataBlocks, %d (period_us), 0x%.8X (Flags)"
//               "Block %d: %d bytes @ 0x%.8X"
struct HssVar {          // 16 bytes / 变量
    uint32_t addr;       // +0x00  变量绝对地址        ← v+0x318
    uint32_t size;       // +0x04  字节数（1/2/4/8）  ← v+0x31C
    uint32_t reserved0;  // +0x08  = 0（memset 后未再写）
    uint32_t reserved1;  // +0x0C  = 0
};

uint32_t n = numSelectedVars;                  // 全局 DAT_14085d1e8
HssVar *list = Alloc((n + 1) * 16);            // ★ +1 个终止项
memset(list, 0, (n+1) * 16);

uint32_t off = 4;                            // ★ 前 4 字节留给时间戳
for (each 选中变量 v, 按符号链 DAT_14286d3b8 顺序) {
    v->sampleOffset = off;          // v+0x38C
    off += v->size;                 // v+0x31C
    list[i].addr = v->addr;
    list[i].size = v->size;
    /* 复位（每次开始采集） */
    v->dataBuf(+0x3D0) = 0;          // 64 MB 环稍后由 FUN_14003e050 分配并清零
    v->lastSamplePtr(+0x3C8) = 0;
    v->field390 = 0;
    v->yAvg(+0x3A8)   = 0;
    v->yMax(+0x398)   = -DBL_MAX;   // 0xFFEFFFFFFFFFFFFF
    v->yMin(+0x3A0)   = +DBL_MAX;   // 0x7FEFFFFFFFFFFFFF
    v->hasData(+0x388) = 0;
}
list[n].size = 0;                            // 终止项（addr 已 memset 为 0）

sampleSize = off;   // 全局 DAT_14085d184 ← 采样包长
rc = JLINK_HSS_Start(list, n, config+0x5A8 /*period_us*/, 1 /*Flags*/);
if (rc >= 0) {

5.2 采样包格式 观测

JLINK_HSS_Read(buf, size) 返回本次读到的字节数，缓冲区内容为紧密排列的定长样本； 变量在样本内的偏移在下发描述符前就已固定（v+0x38C），读取后直接按偏移切片。

实例：3 个变量 g_speed(float32) · g_state(uint8) · g_count(int16) → 样本 = 4+4+1+2 = 11 字节

offset 0timestampuint32 · µs
offset 4g_speedfloat32 · 4 B
offset 8g_stateuint8 · 1 B
offset 9g_countint16 · 2 B
ts (µs) g_speed g_state g_count → 样本首尾相接填满读缓冲

字节序与对齐：探针按目标机的原生布局回传（Cortex-M 为小端），变量紧凑排列、无 padding—— 描述符里的 size 就是真实宽度，因此 uint8 之后紧跟的 uint32 是非对齐偏移。 主机侧 memcpy 到 8 字节槽位时不做对齐假设。

5.3 读取泵 观测

FUN_140040fa0（由 10 ms 周期作业调用）

int bufSize = 0x200000 - (0x200000 % (sampleSize * numVars));   // ≈2 MB
void *buf = Alloc(bufSize);
if (hssActive) {
    int n = JLINK_HSS_Read(buf, bufSize);       // 返回读到的字节数；<0 = 错误
    if (n >= 0) UnpackSamples(n, buf);
}
Free(buf);
if (n < 0) FUN_14003e680();                       // 读取失败 → 停采 + 报错

对齐式的一个"怪味"：缓冲大小按 sampleSize × 变量数 向下取整，而不是按 sampleSize。 因为 Read 本就只返回整样本字节数，这个乘法是过度保守的（每 2 MB 浪费几十~几百字节）， 属于无害的原样照抄即可 —— 但重实现时应改成按 sampleSize 对齐。

为什么要 2 MB：探针在后台按设定周期自主采样并缓存， 主机每 10 ms 批量取走积压数据。JLINK_HSS_Read 只做内存搬运（USB 批量传输）， 采样率与主机轮询频率完全解耦 —— 这是 HSS 能到 µs 级、而"主机轮询读内存"做不到的根本原因。 缓冲取 2 MB 是为了容忍主机侧的调度抖动（10 ms 内探针可产生数十万样本）。

5.5 与 JLink_x64.dll 的交叉验证

J-Scope 只告诉我们"怎么调"，DLL 一侧的字符串则佐证了"调用进去会发生什么"： 

// JLink_x64.dll V9.66 内（字符串常量，非导出符号表）
"HSS started: %d DataBlocks, %d (period_us), 0x%.8X (Flags)"   // ← 证实 (blocks, n, period, flags) 四参
"Block %d: %d bytes @ 0x%.8X"                                  // ← 证实每块 (size, addr)
"HSS sampling rate %d kHz is set too high for this J-Link! Using highest possible rate %d kHz"
"HSS has not been started."   "HSS_Process"   "HSSLogFile"
"Current setup does not support background memory access mode"  // ← HasCapEx(0x35) 失败路径
// 内部命令枚举：CMD_HSS_START / CMD_HSS_STOP / CMD_HSS_READ / CMD_HSS_GET_CAPS
// 命令经 CPU2 固件通道下发：CMD_CPU2_EXEC_CMD (HSS)

这段日志串还给出一个重要事实：HSS 的采样率上限由探针型号决定， DLL 会把过高的周期自动钳到该探针能支持的最高速率 —— 也就是 OpenScope 直接用 HSS 时， "周期设成 1 µs 也不会报错，只会被静默钳位"。这一点在 J-Scope 侧看不到任何反馈（它不检查返回值以外的信息）。

5.6 DLL 侧实证：HSS 全部契约已在主机侧闭环 观测

本轮把 JLink_x64.dll 的四个 HSS 导出逐个反汇编（JLINK_HSS_Start 的核心在 0x1800edb90），J-Scope 调用契约里的每一处"未知"都在 DLL 里找到了对应实现： 

// ── JLINK_HSS_Start(blocks, n, period_us, flags) @0x180108b00 ── 全部为未优化前向参数传递 + 日志
vtable[0x390]()                     // 探测能力：bt eax,0xF（bit15）
if (!bit15) caps = { 5, 50 };        // ★ 回退 caps：最多 5 个变量、最高 50 Hz
else        vtable[0x518](&caps);      // = JLINK_HSS_GetCaps 同一个实现（32 B 结构）

if (!HasHss())              return -4;   // "Target hardware does not support HSS"
if (n > caps.maxBlocks)     return -3;   // "Too many variables specified"
blocksCopy = malloc(n * 16);            // 逐条拷贝 16 B 描述符，同时累加 size
if (!blocksCopy)            return -2;   // "Failed to allocate memory on debug probe"
sampleSize = 4 + Σsize;                  // 与 J-Scope 的 DAT_14085d184 完全一致
rxBuffer  = malloc(0x80000);            // 512 KB 探针侧接收环

period = max(period_us, 1e6 / caps.maxRateHz);   // ★ 静默钳位 + 上面那条 "set too high" 日志
if ((caps.capBits & 2) == 0) flags &= ~1;              // ★ caps.bit1 门控 flags.bit0
vtable[0x528](blocksCopy, n, period, flags);          // 下发给设备层（→ CPU2 固件命令 CMD_HSS_START）
caps 字段（32 B）含义与证据
+0x00 dword最大变量数（cmp n, caps+0; ja → -3）；无 HSS 能力时回退 5
+0x04 dword最大采样率 Hz；DLL 自己算最小周期就用 1e6/caps+4（与 J-Scope 的 TimeResUs 同式）；回退 50 Hz（= 20 000 µs，正是 J-Scope 的 20 ms 回退周期）
+0x08 dword能力位：bit1 门控 flags.bit0；结果另存全局 0x1816d4ac0
+0x0C…+0x1FStart 路径未读取（GetCaps 会填满 32 B，J-Scope 只用了前 8 B）

对 OpenScope 的三条直接结论：

① 三个错误码 -2/-3/-4 完全可以照抄文案与语义（它们就来自 DLL 的这三条分支）；

② 采样周期不需要自己做上限检查 —— DLL 会静默钳位，但 OpenScope 最好把 JLINK_HSS_GetCaps 的 +0x04 读出来主动提示用户"该探针最高 X Hz"（J-Scope 不提示，是个体验缺陷）；

③ JLINK_HSS_Read 的返回值是拷进调用者缓冲的字节数（DLL 内部 mov r8d, eax; memcpy(dst, reply, eax)），按 nBytes / sampleSize 解包是正确用法。
