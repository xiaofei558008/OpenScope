7.2 VarFormat 编码 —— 本次逆向的关键成果

上行通道名形如 JScope_<VarFormat>， 其中 VarFormat 是「类型字符 + 尺寸数字」严格成对的串： 

JScope_t4i4f4     →  时间戳 + int32 + float32
JScope_u2i2u4     →  uint16 + int16 + uint32
JScope_t4f4f4f4   →  时间戳 + 3 个 float32

解析逻辑（FUN_14003fc90）：跳过首个 _ 之前的内容，之后每次固定取 2 个字符（含 t，它同样消耗一位）。

类型字符尺寸数字TypeID含义
t（占位，值忽略）—时间戳标志（置 IsRTTWithTimeStamp）
b15bool
f41float32
f82float64
u1 / 2 / 4 / 86 / 7 / 8 / 9uint8 / 16 / 32 / 64
i1 / 2 / 4 / 810 / 11 / 12 / 13int8 / 16 / 32 / 64
其它——忽略

解析出的类型用于 AddSymbolFromFormat(size, typeID, 0, desc)，描述串即二进制中的：

"%d Byte bool RTT Data %d"      "%d Byte float RTT Data %d"
"%d Byte unsigned RTT Data %d"  "%d Byte signed RTT Data %d"

失败路径的两条原文：

No RTT Up-Channel named "JScope_%Format%" found
The first RTT Channel named JScope_... found did not contain a valid VarFormat

注意 —— RTT-VarFormat 模式下目标端无需 ELF：通道名自带完整布局。 这是与 HSS 模式的本质差异。

7.3 跨读取的样本拼接

RTT 无「整样本」保证，读取会在样本中间截断。J-Scope 用 ≤64 字节的残留缓冲拼接跨读取的半个样本（FUN_140042260）： 

if (targetErrorPending()) { partialLen = 0; /* 清状态 */ }
else partialLen = carryLen;                       // 上次残留

memcpy(buf, carry, partialLen);                    // 先补上残留
n = JLINK_RTTERMINAL_Read(ch, buf + partialLen,
                          min(readBufSize, 0x200000) - partialLen);

total     = n + partialLen;
remainder = total % sampleSize;
UnpackSamples(total - remainder, buf);             // 只解完整样本
if (remainder == 0) carryLen = 0;
else { carryLen = min(remainder, 0x40);             // ★ 上限 64 字节
       memcpy(carry, buf + (total - remainder), carryLen); }

RTT 读缓冲：readBufSize = min(0x2000, channelBufSize)，分配标签 "RTT read buffer allocation"。

7.4 控制通道

FUN_140040ed0 —— 最多 101 次重试

循环最多 101 次：
    n = JLINK_RTTERMINAL_Read(ch, tmp, 256)
    累计满 256 字节 →
        若 tmp[0] != 0 → 报 "Target Error: %s" 并返回失败
        否则返回成功
    Sleep(1)
超时 → 返回 0xFFFFFFFE

架构亮点 —— HSS 与 RTT 共用同一个 UnpackSamples （FUN_14003fa70）：上层数据模型完全统一，只有「字节从哪来」不同。 这是非常干净的抽象。
